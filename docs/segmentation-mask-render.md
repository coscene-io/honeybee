# 语义分割 Mask 的前端 GPU 渲染

分支 `seg-mask-render`（父 `honeybee-seg-port`），日期 2026-11-13。录像 质检测试 CJ260330-3-R154，五路 30 Hz H.264 相机。环境：Apple M4 Max，ego Chromium 156.0.8078.74（ANGLE Metal），viewport 1920×973。

## 结论

**没有用 WebGPU 做主路径，用的是 WebGL2。** 要求写的是 "WebGPU"。我没有默认替换，而是在同一台机器上用同一份 det_seg 形状、同样的位平面和着色逻辑做了两者的对照（`benchmark/mask-gpu-micro.html`，数据见 [WebGPU 与 WebGL2](#webgpu-与-webgl2)）：

- GPU pass 本身都很便宜：每相机 p50 WebGPU 0.066 ms，WebGL2 0.09–0.13 ms。性能不是选 WebGPU 的理由。
- WebGPU 在 40 实例、每帧上传 35 MB 时不稳定：1× 下一次 rAF p50 49.5 ms、78% 帧 >20 ms，复测一次 16.7 ms；4× 和 6× 下 rAF p50 32–50 ms，submit p95 39–60 ms。同条件 WebGL2 rAF p95 一直在 18.6–18.7 ms。
- Image 面板（ThreeDeeRender）已经是 three.js WebGL2 场景。Mask 作为同一场景里共享图像几何的一个 mesh，自动跟随缩放、平移、旋转、翻转和去畸变，而且和图像在同一帧提交。换 WebGPU 要么另起一个画布和合成层、要么把整个 Image 面板迁到 WebGPU。前者两层之间会有一帧以上的错位风险，后者超出本任务。
- 覆盖面：WebGL2 约 97.3%，WebGPU 约 88.6%（caniuse）。Linux 上 Chrome 的 WebGPU 仍不完整。

**主路径**：Image 面板原生 ImageMode 内的 `SegmentationMaskLayer`（WebGL2 `ShaderMaterial`）。RLE 在 Worker 里转成"转置整数位平面"，每个实例占一个 bit（≤8 R8UI，≤16 R16UI，≤32 R32UI，≤64 两张 R32UI），片元着色器 `texelFetch` 后取最高的可见 bit 着色。显示帧和 `topic + logTimeNs` 精确绑定，planes 未就绪就不画（不显示邻帧）。

**回退与降级**（都会在诊断计数里留下记录，不会悄悄发生）：

| 情况                               | 行为                                                |
| ---------------------------------- | --------------------------------------------------- |
| Worker 不可用或出错                | 改为当前任务之后在主线程构建，仍不在 render 帧内    |
| 当前帧 planes 还在构建             | 本帧不画 Mask，`withheldFrames`/`misses` 计数       |
| 单帧 >64 个实例                    | 只画前 64 个，`truncatedFrames` 计数                |
| Mask 尺寸和该 topic 的解码尺寸不符 | 跳过该实例，`sizeMismatches` 计数                   |
| Mask 边长 > `MAX_TEXTURE_SIZE`     | 不画，记错误                                        |
| 无 WebGL2                          | Image 面板本身就无法工作；Mask 没有增加新的平台要求 |

**能否替代多边形渲染：可以，用于显示和播放；编辑仍然是多边形。** 同一构建、同样实例数下，Mask 和多边形的播放帧率几乎相同（1/3/10 实例 1× rAF p95：33.3/66.7/133.4 对 35.1/68.7/133.4 ms），双击进入编辑更快（1 实例 51 ms，旧文档多边形 166.5 ms），播放中 Mask 也可见（旧的多边形路径在编辑会话播放时是隐藏的）。双击只把这一帧这一个实例转成多边形，其余一律保持 Mask。详见 [性能](#性能)。

**主要风险**：

1. **侧栏实例树才是播放瓶颈，不是 GPU。** 3 实例时播放 rAF 每隔一帧 50–66 ms。profile 显示 2.65 s 里只有 27 ms 空闲，`SpatialTree`、`CameraFrameStrip`、`editorTree.selectionStatus` 和 `AnnotationPreview` 合计超过一半主线程时间，Mask 上传 CPU 时间约 0。多边形同样有这个问题（旧文档 10 实例 p95 117.6 ms）。需要单独优化侧栏。
2. **本机标注提交超出 localStorage 配额时只留在内存。** 30 个 Mask 操作提交后刷新页面就丢了（界面提示"仅保存在内存"）。真实服务上线前需要换存储。
3. **WebGL 上下文丢失只在微基准里验证过**（WebGL 恢复约 7 ms、重建约 5 ms；WebGPU 丢失事件 5.4 ms、重建 10.4 ms）。产品里依赖 three.js 自带的恢复，没有在真实页面触发过。
4. **CPU 位平面缓存 96 MB，五路共享。** 32 个实例时每帧两张 R32 平面，每路只能提前约 2 帧，CPU 受限时可能出现不画的帧（计数可见）。
5. **侧栏摘要只覆盖已加载的 10 s 窗口**；窗口边界约有 0.5 s 的加载缝。

## 数据模型

- 一个观测只有一种权威几何。未修改的 Mask 不会被重写。
- 双击进入编辑是临时的多边形视图；移动顶点后提交，这个观测才变成多边形。撤销会恢复原 Mask。
- 合并：任何一侧是 Mask，结果就是一个 Mask（像素并集），`source: "merge"`。
- `source` 只用于标注来源：`mock`、`propagation`、`merge`、`import`。`mock` 是本地合成数据，界面标为 "MOCK · 合成 mask（非推理结果）"。
- 草稿存储键升级到 v3；v2 草稿只读一次，并丢弃其中按画布推算的尺寸。

## 渲染设计

```
document (RLE counts)           Worker                    GPU (per Image panel)
  │  overlaySource:              buildMaskPlanes           SegmentationMaskLayer
  │  topic+logTimeNs → geometry  RLE → 转置整数位平面  →   DataTexture R8/R16/R32UI
  │  稳定 geometry id            LRU 96 MB（五路共享）     texelFetch + 最高可见 bit
  └─ style: visible/selected     预取：时间窗、份额上限     与图像同一帧提交
```

- **转置平面**：纹理第 x 行、第 y 列存像素 (x, y)。COCO 列主序 RLE 的每段 run 因此是连续内存，构建是 O(runs + 像素)。
- **重叠**：每个实例一个 bit，所以重叠区域不会丢实例。着色时选中实例优先，否则取最高 slot；描边约 1.5 屏幕像素，任何缩放下至少 1 个图像像素。
- **稳定 id**：播放中每帧都会注册新帧，geometry id 只在 counts 变化时才变，已构建的 planes 不会因为帧表变化而失效；counts 变了一定换新 id，不会画旧平面。
- **预取**：按时间而非帧数，约两个观测到的显示步长，0.3–1 s、8–24 帧，并且不超过本面板在共享缓存里的份额（`framesAhead`）。
- **不画旧帧**：未就绪就本帧不画，`withheldFrames` 计数。

## 双击转换

- `SegmentationCanvas.doubleClickMask` 用编辑器内容层的屏幕变换把点击点换算到源像素，按"选中实例优先、否则最高 slot"在当前帧找命中的 Mask，与 GPU 叠加层的视觉顺序一致。
- 只转换这一帧这一个实例：`maskToEditorPolygons` 等价于 det_seg `MaskToPolygons(eps=1)`，并补半像素，使多边形和 GPU 填充的像素对齐。
- 返回 IoU（多边形回栅格化后与原 Mask 的交并比）和 `droppedComponents`，写入 `seg-mask-edit-enter` performance measure。
- 实测：3 实例 fixture 双击进入 86 个顶点，IoU 0.9927，转换 1.8 ms（`43-bench-edit-entered.png`）。

## Mock

- `segMockMasks=1`（仅 localhost）：形状来自 det_seg 的 SAM3 视频传播 fixture，确定性映射到每路相机的解码尺寸，并随 log time 平移和形变，相邻帧连续但不相同。
- mock 传播返回 Mask，界面标 MOCK。
- 基准 fixture `segBenchmark={"shape":"detseg",...}` 用同一组形状，可调实例数、`scale`、`fragments`。只在内存中，提交被拒绝。

## 建议

1. **Mask 替代多边形用于显示和播放**，WebGL2 作为唯一路径；WebGPU 等 Image 面板整体迁移时再考虑。
2. **优先优化侧栏实例树**（`SpatialTree`、`CameraFrameStrip`、`AnnotationPreview`），它是多实例播放的瓶颈，Mask 和多边形一样受影响。
3. 本机标注的存储换成 IndexedDB 或等真实服务，避免配额溢出后静默丢数据。
4. localhost 诊断（`__segMaskOverlay`、`__segMaskOverlaySource`）只读、只返回计数，建议保留，便于排查。

### 给后端的反馈

- **重叠**：同一帧多个实例的 Mask 可以重叠，前端按 bit 保留全部实例。后端是否允许重叠、重叠时的语义（谁在上面）需要写进契约。
- **尺寸来源**：`Mask` 没有宽高，前端用该 topic 的解码帧尺寸。建议在 `Mask` 或 `Frame` 上加 `width/height`，至少在服务端校验；否则相机换分辨率或缩放转码后，旧 Mask 会被按错误尺寸解码。
- **谁做 mask→polygon**：前端只在用户双击编辑时转换一个观测，算法与 det_seg 一致。建议后端不要预先转换整段视频，也不要在保存时自动把多边形转回 Mask；如果需要服务端转换，应复用同一份 det_seg 实现，保证双方像素一致。
- **单帧实例上限**：前端单帧上限 64 个实例（两张 R32 平面），超出部分不画并计数。如果业务会超过，需要提前沟通。
